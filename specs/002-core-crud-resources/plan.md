# Implementation Plan: Core CRUD Resources

**Branch**: `002-core-crud-resources` | **Date**: 2026-09-11 | **Spec**: [spec.md](spec.md)

## Summary

Deliver full CRUD (list, get-by-id, create, full-update, partial-update, delete) for the four core
resources — users, products, orders, customers — on top of the Spec 001 foundation, with deterministic
seed data (≥50 users, ≥50 products, ≥100 orders, matching customers), the standard pagination envelope
with `page`/`limit`/`sort`/filter query parameters, and per-resource `zod` validation covering every
category in FR-012 (missing/wrong-type/invalid-enum/out-of-bounds/null/empty/unexpected fields).
Technical approach: one generic in-memory keyed store per resource, hand-written deterministic seed
generators (no new dependency), a shared list-query utility for pagination/sorting/filtering so all four
resources behave identically, and `zod` `Create`/`Patch` schema pairs per resource reused for both
request validation and `PUT`-vs-`PATCH` semantics (see [research.md](research.md) for rationale on each).

## Technical Context

**Language/Version**: TypeScript 5.x on Node.js 20.x (LTS) — unchanged from Spec 001

**Primary Dependencies**: Express 4.x, `zod` (request-body validation, extending its Spec 001 use for env
validation) — no new dependencies introduced by this spec

**Storage**: N/A — in-memory only; one generic keyed store per resource (`users`, `products`, `orders`,
`customers`), seeded deterministically at startup

**Testing**: Vitest + Supertest — unchanged from Spec 001

**Target Platform**: Node.js server (Linux/Windows/macOS), run locally, in CI, and as a target for
external testing tools (k6, Postman, contract-test suites)

**Project Type**: Single backend web-service (REST API server), no frontend — unchanged from Spec 001

**Performance Goals**: List/get/create/update/delete on the seeded volumes (50–100+ records per
resource) respond in low tens of milliseconds under normal load; all operations are O(n) in-memory
array/map operations with no external calls

**Constraints**: No unbounded memory/CPU per request; no external network calls; deterministic seed data
and behavior across restarts (constitution Principle II, NON-NEGOTIABLE); invalid input must never crash
the process (`400`/`422` only); resource identifiers immutable once assigned; cross-resource references
(`Order.customerId`, `Order.items[].productId`, `Customer.userId`) validated synchronously against the
in-memory stores

**Scale/Scope**: This spec only — full CRUD + validation + pagination/sorting/filtering for users,
products, orders, customers, and their seed data; nested/related-resource routes, search, and
authentication are explicitly out of scope (later specs per the project roadmap)
